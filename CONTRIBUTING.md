# Contributing

Thanks for helping make system design easier to learn. Useful contributions include corrections, clearer explanations, accessible diagrams, additional exercises, and well-scoped case studies.

## Contribution principles

1. **State assumptions.** Workloads and guarantees are context-dependent.
2. **Explain trade-offs.** Every added component should solve a named problem and include its costs/failure modes.
3. **Prefer vendor-neutral concepts.** Product-specific examples are welcome when the underlying concept is explained.
4. **Make diagrams accessible.** Add a short textual explanation; SVGs should have a title and description.
5. **Keep learning progressive.** Define a term before relying on it in a later lesson.
6. **Use illustrative numbers honestly.** Label assumptions and avoid implying they are measured facts.

## Pull request workflow

1. Fork the repository and create a focused branch.
2. Make the smallest change that fully addresses the issue.
3. Check local links and Mermaid code fences in the changed Markdown.
4. Preview the rendered Markdown and confirm the diagram has a useful text explanation.
5. Describe the learning outcome and any assumptions in the pull request.

## New lesson checklist

- [ ] Learning objectives are explicit
- [ ] Concepts are explained before jargon is used
- [ ] At least one example or diagram is included
- [ ] Benefits and costs / failure modes are both covered
- [ ] Knowledge check includes useful suggested answers
- [ ] Previous, next, and course-home navigation work
- [ ] Links use repository-relative paths where possible

## Reporting an issue

Include the file path, the unclear or incorrect passage, and a suggested correction or example if you have one. For a design disagreement, describe the workload and guarantee under which your alternative is preferable.
